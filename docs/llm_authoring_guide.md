# LLM Authoring Guide

This guide is for AI coding assistants such as Codex, Copilot, and Claude that
need to build or modify applications using `jinja-bootstrap-spa`.

## What This Library Is

`jinja-bootstrap-spa` is an opinionated framework for:

- server-rendered HTML via Jinja
- Bootstrap 5 visual consistency
- SPA-like fragment replacement through the first-party `data-jbs-*` runtime
- stateful component refresh without a heavy front-end framework

The framework is deliberately narrow. It is meant to make good UI structure
easy to generate and hard to misuse.

## Core Rules

### 1. Keep the server as the source of truth

- Render canonical HTML on the server.
- Return replacement fragments from endpoints such as `/components/orders`.
- Let the runtime fetch and swap fragments.
- Do not move view state into ad hoc client-side stores unless the repo already
  has a deliberate pattern for that.

### 2. Prefer the framework macros first

Before writing custom markup, look for a suitable macro in
`jinja_bootstrap_spa/bootstrap_macros.html`.

Common starting points:

- `page_header(...)`
- `toolbar(...)`
- `table(...)`
- `data_grid(...)`
- `filter_accordion(...)`
- `form_input(...)`
- `form_select(...)`
- `autocomplete(...)`
- `modal(...)`
- `drawer(...)`
- `status_region(...)`
- `toast(...)`

Use raw Bootstrap markup only when the macro surface does not already cover the
interaction.

### 3. Reuse the packaged base template

When the app does not already own a shell, use:

```jinja
{% extends "jinja_bootstrap_spa/base.html" %}
{% import "jinja_bootstrap_spa/bootstrap_macros.html" as ui %}
```

In example-app style setups, `base.html` may also be available through loader
fallback. Either path is acceptable when the app loader provides it.

### 4. Preserve the runtime contract

Interactive fragment roots should use the `data-jbs-*` contract generated by the
framework macros or helpers.

Important attributes:

- `data-jbs-component`
- `data-jbs-endpoint`
- `data-jbs-target`
- `data-jbs-state`
- `data-jbs-key`
- `data-jbs-persist`
- `data-jbs-sse`
- `data-jbs-stream-mode`

Controls should trigger actions through:

- `data-jbs-action="refresh"`
- `data-jbs-action="filter"`
- `data-jbs-action="page"`
- `data-jbs-action="sort"`
- `data-jbs-action="row"`

### 5. Treat state persistence as part of the component contract

For pageable/filterable components:

- keep state in `data-jbs-state`
- keep `state_keys` explicit
- support header persistence when the component opts into it
- preserve visual state across swaps and reloads

For tables, normalize request state on the server before querying.

### 6. Prefer conditional fragment responses

If the server can detect identical fragment output, return `304 Not Modified`
with an `ETag` instead of sending the same HTML again.

This is a first-class part of the intended runtime model, not an optional
optimization.

### 7. Use SSE for live refresh or row-level patching

When a surface is live-updating:

- use `sse_endpoint`
- choose the correct `stream_mode`: `replace`, `prepend`, or `append`
- keep page and selection state stable while stream events arrive
- emit metadata updates when total row counts or page counts change

### 8. Stay within Bootstrap styling

- prefer Bootstrap utilities, spacing, alerts, cards, badges, navs, and forms
- avoid custom CSS unless the consuming app has a clear need
- do not introduce a separate design system when the framework already provides one

### 9. Keep this framework generic

If you are editing this framework repository itself:

- add generic primitives
- avoid domain-specific labels, entities, or workflows
- expose app-specific composition points instead of baking in product language

If you are editing a consuming app:

- build domain-specific macros/templates on top of the generic primitives here
- do not fork the framework macros unless you are changing the framework contract itself

## Recommended Workflow For Agents

1. Search the macro surface before writing new HTML.
2. Check the example apps before inventing a new runtime pattern.
3. Use the smallest existing macro that fits, then compose up.
4. Keep server endpoints fragment-oriented and deterministic.
5. Preserve `ETag`, persistence, loading, and stream behavior when changing interactive components.

For an issue-ready migration brief that can be assigned to Copilot or another
agent in a consuming repository, see
[docs/copilot_migration_issue_prompt.md](copilot_migration_issue_prompt.md).

## Good Patterns

### A stateful page shell

```jinja
{% extends "jinja_bootstrap_spa/base.html" %}
{% import "jinja_bootstrap_spa/bootstrap_macros.html" as ui %}

{% block content %}
  <main class="container py-4">
    {{ ui.page_header(title="Orders", subtitle="Review and operate on live orders.") }}
    {% include "partials/orders_table.html" %}
  </main>
{% endblock %}
```

### A refreshable component

```jinja
{{ ui.table(
  "orders-table",
  "/components/orders",
  columns=columns,
  rows=rows,
  state=table_state,
  total_rows=total_rows,
  persist="header",
  state_keys=["page", "page_size", "sort_by", "sort_dir", "query", "status"],
  sse_endpoint="/events/orders"
) }}
```

### A fragment endpoint

Python:

```python
return conditional_fragment_response(rendered_html, request.headers)
```

Go:

- Normalize incoming state.
- Render the fragment template.
- Return `ETag` + `304` when the fragment body matches the client copy.

## Avoid These Mistakes

- Do not replace Jinja with client-rendered JSON views.
- Do not bypass the macros with bespoke HTML for common controls.
- Do not lose disclosure, paging, selection, or filter state during refresh.
- Do not introduce unrelated front-end frameworks for routine interactions.
- Do not fork the example templates when a shared macro or helper would solve the problem.

## Example Commands

From this repository root:

```bash
npm run example:python
npm run example:go
```

These are the fastest way to inspect the intended interaction model before
generating new pages or components.
